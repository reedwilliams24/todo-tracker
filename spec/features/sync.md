# Sync

Signed-in todos are stored in Supabase and synced across web, iOS and Android. The architecture and
product rules are in [REED-61](https://linear.app/reed-williams/issue/REED-61). This file is the
contract the clients rely on. The client sync engine rules (cache, rollback on failed push, guest
Move/Discard, reconnect) will be added here by the client tickets.

## Server contract

Implemented in `supabase/migrations` and tested by `supabase/tests/database` (pgTAP, CI job
`db-tests-supabase`).

### `public.todos`

One row per todo. Columns mirror [`todo.schema.json`](../schema/todo.schema.json) in snake_case:

| Column         | Type          | Notes                                                                                          |
| -------------- | ------------- | ---------------------------------------------------------------------------------------------- |
| `id`           | `text`        | Generated by the client. Primary key together with `user_id`.                                  |
| `user_id`      | `uuid`        | Set by the server from the signed-in user (`auth.uid()`). Any value a client sends is ignored. |
| `title`        | `text`        | 1–200 characters.                                                                              |
| `notes`        | `text`        | Nullable.                                                                                      |
| `completed`    | `boolean`     |                                                                                                |
| `priority`     | `text`        | `low`, `medium` or `high`.                                                                     |
| `due_date`     | `date`        | Nullable. `YYYY-MM-DD`.                                                                        |
| `reminder`     | `text`        | Nullable. `at`, `1h` or `1d`.                                                                  |
| `recurrence`   | `text`        | Nullable. `daily`, `weekly` or `monthly`.                                                      |
| `completed_at` | `timestamptz` | Nullable.                                                                                      |
| `created_at`   | `timestamptz` |                                                                                                |
| `updated_at`   | `timestamptz` | When the client made the edit. Conflicts are resolved on it.                                   |
| `deleted_at`   | `timestamptz` | Tombstone. Non-null means the todo is deleted.                                                 |
| `server_seq`   | `bigint`      | Sync cursor, assigned by the server on every applied write.                                    |

Timestamps are sent as UTC ISO-8601 (`2026-01-01T09:00:00.000Z`). Postgres returns them as
`2026-01-01T09:00:00+00:00` (fractional seconds only when non-zero), so clients must parse any ISO-8601 offset.

### Write rules

These hold for every write, through `push_todos` or a direct table write:

- **Last writer wins per todo:** an edit replaces the stored row only if its `updated_at` is strictly
  newer. An equal or older edit is ignored.
- **Tombstones win:** a row with `deleted_at` set is applied whatever its `updated_at`, and a
  deleted todo never changes again. Restoring a deleted todo (e.g. undo) needs a new `id`.
- **`server_seq`** is assigned from one sequence on every applied insert or update and ignored in
  input. Writes for one user are serialized until commit, so per user it strictly increases in
  commit order. Values can have gaps. An ignored write keeps its `server_seq`.
- There is no hard delete from clients. Tombstones older than 30 days are purged daily (`pg_cron`).

### Push: `rpc push_todos(rows jsonb)`

`rows` is a JSON array of todos with the column names above (`user_id` and `server_seq` are ignored;
missing optional fields mean null). Returns the **stored** row for every pushed `id`, whether or not
the push was applied, ordered by `server_seq`. If two entries share an `id`, the one that would win
is used. The call is all-or-nothing: an invalid row (e.g. a missing title or an unknown priority)
fails the whole push, and the client rolls back.

```ts
const { data, error } = await supabase.rpc("push_todos", {
  rows: [{ id, title, completed, priority, created_at, updated_at }],
});
```

Errors: `42501` when not signed in, `22023` when `rows` is not an array, `23502`/`23514` for invalid rows.

### Pull

A plain select, protected by row level security (each user only sees their own rows):

```ts
supabase.from("todos").select("*").gt("server_seq", cursor).order("server_seq").limit(500);
```

Apply the rows in order, set the cursor to the last row's `server_seq`, and repeat until a page is
shorter than the limit. The first pull uses cursor `0`. Rows with `deleted_at` set remove the todo
locally. If the last successful pull is older than 30 days, purged tombstones can't reach the
client: pull from cursor `0` and replace the cache.

### Realtime

`todos` is in the `supabase_realtime` publication. Subscribe to `postgres_changes` on
`public.todos` with filter `user_id=eq.<uid>`. Clients only see `INSERT` and `UPDATE` events (deletes
are tombstone updates), each carrying the full new row with its `server_seq`. Ignore events whose
`server_seq` is at or below the cursor.

### Auth

Email code only: `signInWithOtp({ email })` sends a 6-digit code (no link) that expires after
10 minutes, and a new code can be requested after 60 s. `verifyOtp({ email, token, type: "email" })`
returns the session. The email template is `supabase/templates/otp-code.html`, used for both the
magic-link and the confirmation email, with the subject `Your Todo Tracker code: {{ .Token }}`.
